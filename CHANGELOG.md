# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed

- **Every part people wire has a recipe, and "known-good" now means compiled.** All 81 parts and ESP32 features in the knowledge layer carry wiring, Library Manager names and a sketch: 32 new ones this round (SH1106, ILI9341/ST7789, e-paper, seven-segment, BMP180, AHT20, SHT31, SCD4x, ADXL345, LIS3DH, QMC5883L, potentiometer, PN532, MLX90614, MAX30102, MAX6675, ACS712, PCF8574, AT24C EEPROM, SIM800L, RS-485 Modbus, CAN with an MCP2515 or the ESP32's own controller, W5500 Ethernet, I2S audio, MOSFET loads, OTA updates, LittleFS, ESP32-CAM, Bluetooth serial, internet time for India, HTTPS and WebSockets). `npm run knowledge:recipes` compiles every recipe for the Uno, ESP32, ESP32-S2, ESP32-S3, ESP32-C3, ESP32-C6, Pico and Nano ESP32 against a scratch sketchbook (only the libraries a recipe names are visible), and writes the result to `recipes.verified.json`: all 595 recipe-and-board pairs build. A sketch is called known-good only for the families in that record; elsewhere it comes with a warning to compile first.
- **Recipe pins are checked against each chip.** A test runs every recipe's pins through the pin-truth tables for seven chip families and fails on a missing, flash, USB, strapping, input-only, serial-console or (on the S3) PSRAM pin, or two parts on one pin. It found more than 70 unsafe pin choices in the first 49 recipes, mostly strapping or USB pins on the C3 and C6, now fixed; one put a servo on the ESP32-C3's USB pin. Wiring text names the chip's real default I²C and SPI pins, read from the installed cores, and Nano-format boards (Nano ESP32, Nano RP2040 Connect) get Arduino pin numbers instead of GPIO numbers.
- **The IDE speaks the same language as chat mode.** Labels are in sentence case everywhere in the window ("Serial monitor", "Choose a board"; the macOS menu keeps title case, as Mac apps do), the AI is "Impulse AI" in the IDE too, placeholders end in an ellipsis, and tooltips show ⌘ and ⇧ on a Mac instead of Ctrl.
- **Build cards show memory as two short meters** (Flash 313 KB of 1.25 MB, 23 %) instead of repeating arduino-cli's long sentences; the sentences stay under Output. A chat that starts with a build is named after the project, and ports show by their short name.

- **Known-good recipes for the parts people wire most.** Asking for a DHT22, an OLED, a servo, an RFID reader, a stepper, Wi-Fi, MQTT, ESP-NOW, deep sleep or BLE now comes with the wiring for your board, the libraries by their Library Manager names and a sketch that Impulse compiled for the board's chip (Uno, ESP32, ESP32-S3, ESP32-C3), both in `get_component_guide` and alongside the request itself, so the first answer is right without a lookup. Pins differ per chip (the S3's SPI, the C3's few GPIOs), and a part a chip lacks (touch on the C3) gets no recipe rather than a wrong one.
- **The agent finishes its sentence.** A long job used to end with "Maximum iterations reached. Please refine your query." after it had in fact compiled and uploaded. The step budget is larger, and when it runs out the agent says what it did, what works and what is left.
- **Impulse Cloud runs as a container.** A Dockerfile and a deployment guide for Google Cloud Run (free tier, UPI billing in India, Neon for the database); the server listens on every interface when `HOST` says so.
- **One Impulse AI.** The model menus are gone from chat mode and the IDE, and answers say "Impulse AI". Before every turn the app asks the server which model answers this kind of work; the server picks the cheapest one that does the job from the admin console's new Routing table (agent, plan, debug, ask, summaries) and climbs an escalation ladder when a turn has already failed a compile or a check, so a retry is smarter than the first try. Admins still see and set models; people do not.
- **Paid models only.** The free models that ran on this computer through Ollama are gone, from the model menus, the sign-in dialog and the account footer. Every build is credits-only: a build without a cloud address has no AI (the simulator and the IDE still work).
- **GPT-5 models through Impulse Cloud.** The gateway gained an OpenAI lane next to the Anthropic one: GPT-5.4 (the default), GPT-5.5, GPT-5.4 mini and GPT-5.4 nano, priced from OpenAI's list and charged in credits like the Claude models, with prompt caching, one answer per request and storage at the vendor turned off. A vendor without a key on the server is simply not offered, so the menu only shows models that work. The desktop app talks to that lane with its own small client for OpenAI's Responses API (streamed, tool calls assembled, the model's reasoning carried across the tool steps of a turn, retries that honour the server).

### Fixed

- **Sign-up limits could be dodged.** The server also trusted a client's own X-Real-IP header, so someone could invent an address per request and get a fresh sign-up allowance each time (and with it the welcome credits). Only a single-address X-Forwarded-For counts now; a test reproduces the trick.
- **Libraries install themselves for every recipe.** The library index lists which headers a library provides for fewer than half of its releases, and for none of GxEPD2, WebSockets, OneWireNg or the SparkFun MAX3010x library, so the first build of ten recipes stopped at a missing header instead of installing the library. Impulse's own table of header owners now covers every header a recipe includes, HX711.h goes to the HX711 library the recipes and most tutorials use, and a test fails if a recipe ever includes a header the installer cannot trace. A sketch that includes two headers of one library installs it once ("Installed OneWireNg, OneWireNg" is gone). Checked in the app: the ESP32-C6 DS18B20 recipe built from an empty sketchbook, installing OneWireNg by itself.
- **Two recipes did not build on some boards; the compile check caught both.** The DS18B20 on an ESP32-C6 now uses OneWireNg's own driver, because OneWire 2.3.8 does not build for that chip. ESP-NOW picks its receive callback by core version, so the same sketch builds on core 3.x and on the 2.x core Arduino ships for the Nano ESP32. A Nano ESP32 selected through Espressif's core now gets Arduino pin numbers, as it does on Arduino's core, instead of a classic ESP32's GPIO numbers.
- **A server with no sign-in method switched on** showed an empty sign-in dialog; it now says sign-in isn't open yet. Smoke and end-to-end tests and the live checks run with `IMPULSE_CLOUD_URL=off`, so they never talk to the live cloud now that builds have its address.
- **The Problems tab explains first, then shows the compiler.** Impulse's own sentence about a failed build reads as a sentence above the compiler's lines, which are no longer each boxed in red italics; an empty tab says "No problems"; a missing board or sketch is said once, not once per click. The "Error Analysis" block that printed an internal error type after every failed build is gone: fixes that worked before still show, built from plain text, so an `#include <Wire.h>` in one no longer vanishes or runs as HTML.
- The board dialog, the Tests hint and the Hardware tasks panel use sentence case and plain words ("Choose a board to verify your sketch, and its port as well to upload it"), the Tests and Hardware tasks panels no longer show their source indentation as a blank line or a run of spaces, and Hardware tasks has a real empty state and a trash icon. The AI is told to point people to Choose a board instead of a dropdown that no longer exists.
- An example opened with no board chosen now chooses its own (Verify used to do nothing). A hidden item in the IDE's status bar showed as a stray dot. The simulator panel said Ctrl+Shift+S toggles it (that is Save As); it is ⌘⇧D. The plotter drew in its own bluish colours with "..." text in a tiny font; it uses the app's colours, real icons and a proper empty state. The serial monitor's Clear and Send buttons, and the library buttons, were square, uppercase or monospaced unlike every other button. The board menu had an empty gap above its first item.
- **No more installing a library for a header the core already has.** `#include <esp_sleep.h>` (and `driver/…`, `freertos/…`, `avr/io.h`, `<vector>`…) made the build installer fetch a stray library that ships a copy; such headers are never treated as missing.
- **Native USB boards after a reset or deep sleep.** An upload waits up to 20 seconds for a port that comes and goes (a board in deep sleep shows its port only while awake) instead of failing at once, the serial monitor finds the port again within about half a second (it polled every 3 s), and the AI knows that the first lines printed after a wake are lost unless the sketch waits, that ESP32-S3 touch values rise when touched, and how to read the chip temperature.
- Long sketch names in chat mode's sidebar spilled past the edge and made the list scroll sideways; the "Sharing fixes" line in the account menu was cut mid-sentence; the background character field is quieter, especially in the light theme; the IDE's serial Send button and "Baud rate" label match the rest of the app; the welcome toast has a title.
- **The simulator check installs the libraries a sketch needs.** Chat mode's check after every AI edit compiled without installing libraries, so any sketch with `#include <DHT.h>` or an OLED failed with "No such file or directory" while the Run button installed the library and worked. That gap is what made simulations look broken and sent the AI rewriting correct code. Every compile for the simulator now installs what the sketch's includes need (from the library index), then anything the compiler still misses, in rounds; builds for the board do the same. Eleven of the 49 examples went from failing to passing in chat mode.
- **Headers go to the library that owns them.** The library index does not say who provides `Adafruit_GFX.h`, and a stray library that ships a copy won, or `Servo.h` picked a board vendor's library instead of Servo. A table of the well-known headers now settles those, a library named like the header outranks one that merely provides it, and headers the board's own core provides (`Wire.h`, `WiFi.h`…) are never "installed". Seven more examples pass because of it.
- **The serial monitor finds the board again after an upload on macOS.** arduino-cli names a port `/dev/cu.…` while the serial library lists `/dev/tty.…`; the reconnect compared the two and gave up. Verified on a real ESP32-S3: upload while the monitor is open, and it says "Reconnected" and keeps printing.
- **Tools › Serial Plotter shows the plotter.** It switched the sidebar to the serial panel afterwards, which brought the Serial output tab back in front.
- **The ESP32 check is steady on a busy computer.** Under load the firmware's last serial lines arrived after the check stopped reading, and the emulator's first run after launch could drop a few pin edges, so a correct 2 Hz blink failed "serial contains" or "frequency". The check now gives the stream a moment before it reads, and runs a timing check once more before calling it a failure.
- The credits countdown could say "in 4 h 60 min"; it says "in 5 h".
- The AI's simulator feedback named pin activity with the wrong field names, so it always said "No pin changed". Tools › Get Board Info without a port now shows a visible hint.

### Added

- **Compile errors explained without the AI.** An error decoder knows 56 common Arduino compile and link errors (core 2 code on ESP32 core 3 and the reverse, AVR limits, missing includes, pasted curly quotes, a missing brace or setup(), linker errors…). The Problems tab and the build card lead with its cause and fix instead of "the sketch has a compile error", and the AI's compile result carries them. Where the fix is mechanical, a rewrite applies it (LEDC and timer calls between core versions, ESP-NOW callbacks, includes, quotes, braces). `npm run knowledge:errors` proves the rules: each rule's broken example is compiled on the real core, the real output is kept as a test fixture, and the rewritten example must compile; 39 rules are proven that way (proof L3). The real compilers corrected the knowledge on the way: `neopixelWrite` was never removed in ESP32 core 3.3 (the drift note said it was), the Uno's core defines A6 and A7, and AVR builds with `-fpermissive`, so comparing a char with a string is only a warning there.
- **A hardware linter.** 28 rules find what compiles but fails on the board, or will not compile on this core: an ADC2 pin read with Wi-Fi on, delay() or printing inside an interrupt, a shared variable that is not volatile, an ESP32 interrupt handler outside IRAM, the wrong core's LEDC, timer or ESP-NOW API, prints lost before a native-USB board's serial monitor reconnects, `while (!Serial)` that never ends on battery, millis() in an int, AVR limits (pull-downs, printf, fixed I²C pins, PWM pins, A6/A7), emulated EEPROM without begin/commit, a missing Serial.begin. Every build runs it: findings go to Problems (without taking focus from a build that worked) and the build card, the AI's compile result carries them, and the AI's verify step sends its errors back to the model before an answer stands.
- **EmbedBench, a benchmark for embedded AI** (`npm run bench`, `bench/`): 60 tasks on the Uno, ESP32, ESP32-S3, ESP32-C3, Pico and Nano ESP32, each with the request as a student would type it, the circuit, checks the simulator runs, and a reference sketch that passes them. It scores the same model alone, with Impulse's knowledge, and with Impulse's verify loop (linter fixes, compile, decoder rewrites, one repair round), and reports the pass rate and the cost per working sketch.
- **Every fact says how it is known.** Impulse's knowledge now carries a proof level, from L0 (not yet checked) through L2 (read from the installed core), L3 (compiled by Impulse) and L5 (ran on a real board) to L6 (fixed real users' builds), in every tool answer and in the facts that ride with each request. The AI is told to prefer proven facts to its memory and to say when something rests on an unchecked note. `npm run knowledge:audit -- --write` and `npm run knowledge:probe -- --write` record what they proved in `knowledge/proofs.json`: 50 catalog boards and 8 chip pin tables checked against the installed cores, and the probe sketches for AVR, ESP32, the Nano ESP32 and the Pico compiled. A proof is bound to the text it proved, so editing a probe or recipe voids it until it passes again. Both scripts also stopped ignoring the first board or probe named on the command line.
- **Impulse Cloud is live** at https://impulse-cloud-1008821972739.us-west1.run.app (Google Cloud Run in Oregon beside a Neon Postgres database in AWS Oregon), and builds point at it. It is set up to cost nothing at launch: it scales to zero with at most two instances, old images and uploaded sources are cleaned up automatically, a budget alert fires at the first rupee spent, and the AI stops for the day after $2 until the owner raises it. Oregon rather than Singapore because Cloud Storage and Cloud Run's outbound data are only free in the US, and OpenAI runs in the US anyway. `cloud/scripts/set-signin.sh github|google <client-id>` turns on a sign-in method from a client secret on the clipboard.
- **A deployment guide for Google Cloud Run** (`cloud/DEPLOY.md`): billing with UPI, the project and services, Neon in Singapore beside the server, an OpenAI key with a hard monthly cap, Secret Manager, the deploy command, Google and GitHub sign-in, Resend, pointing the app at the server, updates, rollbacks, costs and a troubleshooting table. `.gcloudignore` keeps the local `.env` out of the upload.
- **The knowledge layer's strategy** (`docs/design/knowledge-strategy.md`): proof-carrying knowledge, the engines that check the AI's work, the fix flywheel, a nightly benchmark, and the build plan, for the owner's review.
- **The serial monitor keeps up and comes back by itself.** Lines are assembled in the main process, kept in one history of the last 5,000 and sent to the window in batches, so a sketch printing at 115200 no longer outruns the pane, a line that never ends in a newline still shows, and switching between chat mode and the IDE loses nothing (the pane fills in what it missed). An upload now hands the port over: the monitor closes, the upload runs, and the monitor reopens when the board comes back, from anywhere you upload. The AI reads the same history, so it can see what your board printed even when you opened the monitor yourself.
- **Libraries install themselves.** A build that fails on a missing header looks up which library provides it, installs it and builds again, saying so in the output. Chat mode has its own Libraries dialog (what this sketch needs, search, install, remove), so it no longer sends you to the IDE, and the AI has a `libraries` tool: it searches the index before naming a library and says when nothing matches, instead of recommending something that does not exist.
- **Files you can manage.** New file, rename and delete (to the Trash, so it can be put back) in a Files tab in chat mode's side panel. Deleting a file was not possible at all before.
- **Pins that exist on your board.** Impulse knows which pin numbers each chip really has, which are flash, input-only, strapping or USB, and checks the pins a sketch uses against the board you selected, resolving `#define`s and the core's own names. Every build reports it in the console, the build card and the AI's result: "the ESP32-C3 has no pin 22 (LED = 22). Its pins are 0–21." A sketch like that compiles happily and fails on the bench, which is how a wrong GPIO used to reach you. The installed core outranks the table, so a board that exposes more than its chip's baseline stays correct. `npm run knowledge:audit` checks the whole knowledge layer against the installed cores.
- **The AI reads the board maker's documentation.** A `read_docs` tool lists the official pages for your board and its chip (Arduino, Espressif, Seeed, Adafruit, PJRC, M5Stack and others) and reads one, cached for a week. Only the page's address is requested: never your code, prompt or circuit.
- **Uploads ask in the conversation**, with the sketch, board and port named, instead of a system dialog over the window; and when an upload cannot happen, Impulse says exactly why. Upload and Verify now sit beside the board chip, where the board is chosen.
- A failed simulator check goes back to the AI once by itself, with what the sketch printed, what the pins did and what is wired, and with instructions to say when a check could never pass with that wiring rather than twisting the code around it.

- **Builds and uploads stream live.** Every line the compiler and the upload tools print appears as it comes: in the IDE's console, on the Verify/Upload buttons and a new footer item ("Linking…", "Uploading 45%"), and in chat mode as a build card that becomes a saved record. The result is Arduino IDE's two memory lines (flash and RAM, used and maximum) or a named failure with what to do: "The sketch is too big: 41,552 bytes, and this board's flash holds 32,256", a missing library by header, "the board did not answer the programmer", "the ESP did not enter download mode", a port in use, a Pico not in BOOTSEL mode. One build runs at a time: asking again joins it, a different build is refused while one runs, and an upload is one job with a compiling stage and an uploading stage, so nothing says "compiled" halfway through. Builds stop when they print nothing for a while instead of at a fixed two minutes, which cut off first ESP32 builds. The AI's compile and upload tools get the same facts and a BUSY note that tells the model to wait.
- **Code the AI writes goes into the sketch.** The agent is told to write with its editor tools, never to paste a sketch for you to insert, and when an answer carries a whole sketch anyway it is written into the open sketch and saved; that code block shows "In the sketch" instead of Insert, and Revert on your message still puts the code back.
- **The agent sees the circuit you wired.** The simulator's circuit (saved as `diagram.json` next to the sketch) goes with every request: the parts, the board pin each is wired to, the wiring check's warnings, and whether you or Impulse's circuit builder made it; the agent says when it changed, has a `get_circuit` tool, and suggests drawing the circuit in the simulator when it needs to see the hardware. The file remembers who last changed the circuit, so a later chat still knows it is yours.
- **A knowledge layer for the 100 boards India uses most.** A ranked catalog of boards (Uno and Nano clones, ESP32 dev kits and the ESP32-CAM, NodeMCU and D1 mini, Pico, Blue and Black Pills, Nucleos, Uno R4, XIAO, Teensy, ATtiny…) with notes per family (how it uploads, how it is powered, what clones do, which libraries fit), a record per board (onboard parts and the pins they take, the upload procedure, traps) and API-drift tables per core version (ESP32 core 3.x: LEDC, timers, ESP-NOW callback signatures; ESP8266 3.x; Arduino-Pico 4.x; Uno R4; SAMD; Nano Every; mbed; STM32duino; Teensy). The selected board's notes travel with every request after the core's own pin facts; `get_board_info` returns the full notes; `search_boards` searches the catalog first and names the core a board needs. The board picker lists the popular boards first, grouped by family and badged "simulates" or "core download", and installs a missing core when you pick its board (ESP8266, STM32, Uno R4, SAMD, mbed Nano, Due, Seeed, Adafruit nRF52, Teensy, Digispark, megaTinyCore). Probe sketches compile the notes' advice against the real cores (`npm run knowledge:probe`).
- **Learning from fixes.** When a failed compile or upload is followed by a success, Impulse records the fix: the error's signature, the board and core version, the libraries in play, a diff of only the lines that changed, and whether the agent or you changed them (SSIDs, passwords, keys, emails and home folders redacted). Fixes stay on this computer and, when you are signed in with **Sharing fixes** on (account menu), go to Impulse Cloud, which counts them per error. The next time anyone hits that error, the agent's compile result carries the known fixes before it guesses. The admin console gains a Learning page. PRIVACY.md describes exactly what is kept.
- **A leaner AI harness.** Agent mode starts with 13 tools instead of 28 (one `serial` tool replaces eight; boards, memory, project and playground tools load as packs when a step needs them), Debug mode can read, edit, compile and watch serial, and a verify guard compiles an edited sketch before the model's "done" stands, sending a failure back to the model with the diagnostics. Every model call of a turn carries a task id, so the cloud can add up what one request cost.
- **Credits-only builds and faster refills.** A build with a cloud address runs its AI through Impulse Cloud alone (local Ollama models exist only in development builds). The Free plan refills 25 credits every 5 hours instead of 100 a month (plus the 200 welcome credits), editable in the admin console; the account panel, the plans dialog, the sign-up page and the out-of-credits notice say so and count down to the next refill.

- Impulse now opens in **chat mode**: one conversation to plan, build and debug, with the IDE one click away (the Chat | IDE switch, ⌘E). Say what the board should do; the agent writes the sketch into a project of its own (the sketchbook's "Impulse Projects" folder), wires and runs it in the simulator, and shows the result as a card under the answer with "Watch it run" or "Fix it". Three modes: Agent builds, Plan lays out parts, wiring and steps without changing anything, Debug finds out why something fails. A side panel shows the simulator, the serial monitor and the code (the same live circuit and the same editor document as the IDE); the board chip, Verify and Upload are in the top bar and the "+" menu; chats are saved with the projects they build (rename, delete with Undo, ⌘K search, "pick up where you left off"); and the IDE's chat panel shows the same conversation. Before the first message the screen is a field of firmware hex lit by slowly drifting light, and a click anywhere sends a ripple of light running out from it, a third of the window wide and gone in under three seconds (several clicks overlap and dissolve together, each ripple keeping its own pattern); it goes once the conversation starts. Every number in the effect is a parameter, and `npm run field-lab` builds `docs/design/field-lab.html`, a standalone page with a slider for each one to tune the look live.
- **Impulse accounts and credits** take the place of API keys. Sign in with Google, GitHub or email + password (verified with a 6-digit code) and the AI runs on Impulse's own key: new accounts get 200 free credits, the Free plan adds 25 every 5 hours, and Pro and Max add more every month (until online payment arrives, upgrades are requests the Impulse team approves). The remaining credits are a ring under the chat box, each answer shows its model, time and cost, and running out points to the plans or to a free local model. Email accounts sign in inside the app; Google and GitHub sign in in the browser, which hands the session back to the app on this computer only. Free local models through Ollama keep working without an account.
- **Impulse Cloud** (`cloud/`), the server behind the accounts: Better Auth, the credit ledger, an Anthropic-compatible AI gateway that checks the account, plan, credits, request rate and the day's budget before paying for a request and charges what the answer actually cost, and an admin console (`/admin/`) with sign-ups, usage and cost, each user's ledger, credit grants, plan changes, upgrade requests, suspensions, an audit log, and prices, limits, models, maintenance mode and an in-app announcement that change without a deploy. It runs on Vercel and Postgres; `cloud/README.md` has the runbook, and CI runs its tests against a real Postgres.
- AI answers are rendered as Markdown (headings, lists, tables, quotes, links, code blocks with Copy) in chat mode and in the IDE's chat.
- ESP32 simulator: SPI is bridged, so `SPI.transfer()` reaches the circuit's parts; QEMU images are built for dual I/O flash, so boards whose core names quad or octal flash start instead of asserting. `impulse-test` shows the last serial lines when a sketch crashes or hangs, not only when a check fails.
- Every board in the board menu now runs in the simulator (242 boards from the installed cores, 253 with their CPU options; each one is compiled and run in a check).
- ATmega32U4 boards run in the simulator: the Leonardo (new drawing), Micro, Leonardo ETH, Esplora, Yún, Yún Mini, Linino One, Chiwawa, Robot Control, Robot Motor, LilyPad USB and Circuit Playground Classic. Their Serial is the chip's own USB port, so the simulator emulates the 32U4's USB controller and a computer that enumerates it and opens the port (`while (!Serial)` works, and typed text arrives); Serial1 is the UART on pins 0/1. analogWrite works on all seven PWM pins, including 6 and 13 on Timer4.
- Also new: the Arduino NG with an ATmega8 (its own register map), the Gemma (an ATtiny85 on Arduino's core) and the Uno WiFi (its ATmega328P). Boards that run at 8 MHz (LilyPad USB, Circuit Playground Classic, Gemma) are compiled for the simulator's 16 MHz, so their timing is right.
- ESP32 boards run in the simulator: every board of Espressif's ESP32 core built on the ESP32, ESP32-S2, ESP32-S3 or ESP32-C3 (214 boards: DevKits, XIAO, Feather, Heltec, TTGO, LOLIN…) and the Arduino Nano ESP32. The real firmware runs in Espressif's QEMU, compiled for the board you picked with its own pins and options, with Espressif's core 2.x or 3.x. New drawings: ESP32 DevKit V1, ESP32-S3 DevKitC-1 (its RGB LED lights up), ESP32-C3 DevKitM-1 and the Nano ESP32; other boards are drawn on their chip's DevKit and wired by GPIO number, and ESP32-S2 boards (which QEMU doesn't emulate) run on the S3 with their own pin definitions.
  - Pins, buttons and interrupts, analogRead, PWM (analogWrite, LEDC on cores 2.x and 3.x, tone), the RGB LED, pulseIn (ultrasonic sensors) and I²C (Wire) work with the simulator's parts; Serial is the serial pane. A small bridge compiled into the simulated sketch (never into uploads) connects the firmware to the circuit.
  - Wi-Fi: the emulator has no radio, so WiFi.begin() joins a pretend network and gets IP 10.0.2.15, and scans find two networks, so sketches run past their Wi-Fi setup; requests to the internet get no answer.
  - The emulator ships inside the Mac app. On Windows and Linux it downloads from Espressif the first time you simulate an ESP32 (you're asked first; about 4–40 MB), checked against its published checksum; on Linux it uses the system's pixman, libgcrypt, SDL2 and libslirp, and names the packages to install if one is missing.
  - Six ESP32 examples (blink, dimmer, Wi-Fi status light, S3 RGB LED, C3 button interrupt, Nano ESP32 blink), and impulse-test runs ESP32 sketches too (`--fqbn esp32:esp32:…`).

- The AI knows your board instead of guessing. Every request carries the selected board's real facts, read from its installed core the way the compiler sees them: the chip, clock and logic voltage, what LED_BUILTIN really is (a plain LED, an RGB NeoPixel such as the ESP32-S3's on GPIO48, or not defined at all), and the I2C, SPI and Serial pins. Four new agent tools go further:
  - get_board_info: any installed board's pins, analog and touch pins, memory, board options (such as USB CDC On Boot) and traps, from any core.
  - get_mcu_guide: rules for 24 chip families, from the ATmega328P, Mega and Leonardo through megaAVR, ATtiny, SAMD, Renesas (UNO R4), nRF52840, RP2040/RP2350, every ESP32 variant and the ESP8266, to STM32, Teensy and the UNO Q. It covers voltage and current limits, pins to avoid, ADC/PWM/timer behaviour, USB Serial, the ESP32 core 2.x → 3.x API changes, and common mistakes, plus embedded fundamentals.
  - get_component_guide: 65 sensors, displays, drivers and modules with their interface, voltage, I2C addresses, library and wiring pitfalls, found by name or by I2C address.
  - search_boards: any board's FQBN and the core it needs, installed or not.

  When the board changes mid-conversation, the AI is told that earlier answers were for the other board.

### Removed

## [2.0.0-beta.1] - 2026-10-12

### Added

- The AI chat's composer is a glowing pill. On send it folds into a ball, flies up into the conversation and becomes a dotted orb whose label follows what the agent is doing (reading the sketch, writing code, compiling, uploading…), then turns green, condenses and unfolds into the answer card, which stays in the chat. Errors resolve red with "Couldn't finish". It follows the light and dark themes and, with reduced motion, cross-fades instead of moving. The agent now reports each step to the chat as it happens.
- ATtiny85 in the simulator: ATTinyCore firmware runs on an emulated ATtiny85 at 16 MHz, drawn as a DIP-8 chip that plugs across a breadboard. Digital pins PB0–PB5, PWM on PB0 (Timer0) and PB1/PB4 (Timer/Counter1, modelled from the datasheet's fast PWM), the 4-channel ADC with its 1.1 V and 2.56 V references, INT0 and pin-change interrupts, EEPROM and the watchdog. ATTinyCore's software Serial is decoded from PB0 at whatever baud the sketch uses, and typed text goes in on PB1 through the analog comparator interrupt, half duplex like the real chip. The USI is modelled from the datasheet, so Wire (I²C: LCDs, RTCs, sensors) and SPI work on PB0–PB2, and the editor warns when a sketch uses Serial and I²C, which share PB0. The debugger works on it. The circuit check asks for a 2.7–5.5 V supply and warns about PB5 being the RESET pin. The first ATtiny85 build offers to install ATTinyCore (about 10 MB). Three examples (blink, a dimmer, an I²C LCD), and impulse-test runs ATtiny85 sketches too.
- Source Control panel (View › Source Control, ⌘/Ctrl+Shift+G): start a Git repository with a .gitignore for build output, see changed files and their diffs, commit everything, pull (fast-forward only) and push, and browse recent commits. It asks for a name and email once per repository instead of letting git invent one from the computer's name.
- Raspberry Pi Pico in the simulator: Arduino-Pico firmware runs on an emulated RP2040 (rp2040js) with GPIO, PWM, the ADC, I²C, SPI, Serial over USB and Serial1/2, at 3.3 V logic with pull-ups and pull-downs. Every simulated part works with it; the circuit check flags 5 V signals into its pins. The first Pico build offers to install the Arduino-Pico core (about 450 MB). Switching between an Uno and a Pico keeps wires on the matching pins. Two Pico examples, and impulse-test runs Pico sketches too. The debugger stays AVR-only for now.
- Capacitors charge and discharge in simulated time: RC delays, button debouncing, PWM smoothed into a voltage, and analogRead along the charging curve all behave like the real circuit (within about 1% of the RC formula in the tests). The inspector shows the voltage across each capacitor, and a new example plots the RC curve.
- PlatformIO projects: a folder with platformio.ini is built and uploaded with PlatformIO Core. Choose the environment in the status bar; Arduino-framework environments for the Uno, Nano and Mega 2560 can be simulated, debugged and tested like sketches, with diagram.json at the project root.
- Debugger for the simulated Uno, Nano and Mega: breakpoints in the editor gutter, step over/into/out, run to cursor, the call stack (unwound from the compiler's frame information, with each frame's locals), and the values of locals, globals and registers in a Debug tab, with changed values highlighted. Debug › Start Debugging (F5). Debug builds are compiled with -Og and without link-time optimization so every line can be stopped on.
- `impulse-test`: hardware tests on the command line and in CI. It compiles each sketch, simulates it with its `diagram.json` circuit, checks its `// @expect` lines, fails on short circuits, and writes human, JSON or JUnit reports with exit codes for CI. Releases include it as a single file that needs only Node.js and arduino-cli (docs/TESTING.md).
- First-run setup: when arduino-cli, the AVR core or (on Apple silicon) Rosetta is missing, Impulse explains what's needed and installs it with progress. arduino-cli 1.5.1 is downloaded from its official release and checked against a SHA-256 built into the app. Existing installs, including the one inside Arduino IDE 2, are found and used. Tools › Set Up Arduino Tools reruns it.
- Release pipeline: pushing a version tag builds macOS (Intel and Apple silicon), Windows and Linux installers with auto-update metadata into a draft GitHub Release; signing and notarization run when the certificates are configured.
- PRIVACY.md, SECURITY.md (private vulnerability reporting), CONTRIBUTING.md, THIRD_PARTY_NOTICES.md (`npm run notices`), Dependabot, and issue forms for bugs, features and part requests. Privacy and open-source licenses are readable in Help › About.
- `npm run test:e2e`: opens an example, compiles and runs it, presses its button, and audits accessibility (axe) on the main screens in both themes; runs in CI on all three systems.
- Keyboard and screen-reader access in the simulator: `[` and `]` select parts, the selection is announced, and part settings are labelled controls in the inspector. The part picker follows the combobox pattern.
- Help › Report a Problem: review exactly what will be sent (version, OS, recent errors with your home folder and keys removed), then open a pre-filled GitHub issue. Nothing is sent from the app itself.
- Crash recovery: a crashed window offers to reload, and the next launch offers to report what happened.
- "Request this part" in the part picker when a search finds nothing.
- Board options (Tools › Board Options, or the board menu): USB CDC On Boot, flash size, PSRAM, CPU speed and the rest, saved per board and used for verify, upload, export and the AI tools. An ESP32 on its built-in USB port gets "USB CDC On Boot" turned on automatically so its Serial output shows up.
- The Serial Monitor reopens by itself after an upload, as in Arduino IDE 2.
- Port lists name the USB chip when the board isn't recognised (Espressif native USB, CH340, CP210x, FTDI…) and list USB ports first; Bluetooth and system ports appear under "Show all ports".
- Simulator boards: Arduino Nano and Arduino Mega 2560 (ATmega2560: ports A–L, timers 0–5, Serial1–3, 16 analog inputs) alongside the Uno; switching boards keeps wires on matching pins.
- Circuit engine with real nets and voltages: pull-ups, voltage dividers, breadboards (full, half, mini), short-circuit detection, and parts that react to each other as well as to the Arduino.
